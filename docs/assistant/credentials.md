# Assistant credential storage

## Trusted-process boundary

Persistent provider credentials are resolved inside the Electron main process and its in-process
backend. The framework-independent contract is
[`SecretStore`](../../src/core/contracts/credentials/secret-store.ts): asynchronous `get`, `set`,
`delete`, and `listRefs`. Values must never be exposed through renderer IPC, provider DTOs, task
snapshots, logs, or exported diagnostics. `listRefs` is trusted-only and returns references, not
values. `core.secret-store` is the backend SDK injection token; Electron supplies the implementation
through [`credential-runtime.ts`](../../electron/src/main/credential-runtime.ts).

Provider references are opaque `provider/<UUIDv4>` values generated by trusted code. The generic
vault also reserves `session/<UUIDv4>` for a future trusted session adapter. This reservation does
not install or enable SIWC, expose session credentials, or establish licensing approval.

This vault protects persistent secrets and narrows privileged credential IPC. A separate
per-launch application boundary authenticates Assistant/Tasks REST and SSE, legacy aliases,
provider configuration and probes with `X-OpenPCB-Token`, exact backend Host/port and exact
renderer Origin. Electron main generates that token in memory and supplies it only through
the validated `local-api:bootstrap` handler to the current trusted main window's main frame.
It is never a provider credential, persistent renderer setting, query token or MCP bearer.
Missing application token configuration fails closed in standalone development as well.
Provider create/update REST operations reject credential fields; the settings UI submits keys
only through typed IPC. CORS is not authorization. See the
[local application boundary and explicit development setup](../../DEVELOPER.md#security-model).
The vault alone does not close OPENPCB-114's full acceptance matrix or OPENPCB-93's broader scope.

The design also does not defend against arbitrary code execution in the trusted process, an
attacker running as the same OS user with access to the app and keychain, or compromised provider
endpoints. OS encryption is not a substitute for those boundaries.

## Renderer credential API

[`RendererCredentials`](../../src/core/contracts/credentials/renderer.ts) exposes only:

```typescript
window.electronAPI?.credentials?.set({ providerId, apiKey });
window.electronAPI?.credentials?.clear({ providerId });
window.electronAPI?.credentials?.status({ providerId });
```

Each call returns `{ ok: true, value: { configured: boolean } }` or a sanitized error with a static
code and message. The renderer can submit a newly typed key but cannot retrieve a saved key or
select an arbitrary secret reference. `configured` describes provider configuration; it is not
proof that a keychain is currently unlocked or that a provider accepts the key.

[`credential-ipc.ts`](../../electron/src/main/credential-ipc.ts) requires the exact current main
window's web contents, its main frame, and the configured renderer origin. Development allows
only `http://127.0.0.1:1420`; packaged runs use the embedded backend's actual origin. Unknown
windows, subframes, absent frames, destroyed windows, other ports, and other origins are refused.
Requests reject extra fields and arguments. Provider IDs allow `[A-Za-z0-9_-]{1,128}` except
prototype-property names. API keys are nonempty, limited to 16 KiB in UTF-8, and reject control
characters. No `credentials:get` handler exists. Provider service exceptions are reduced to
static public errors; their original messages and stacks are not returned or logged by the vault.

## On-disk protocol and durability

[`CredentialVault`](../../electron/src/main/credential-vault.ts) stores `credential-vault.json` in
Electron's `userData` directory. The outer document identifies
`format: "openpcb-credential-vault"` and `version: 1`. Each nondeleted entry is base64 encoding of
OS-encrypted bytes, not base64 encoding of a plaintext secret. The encrypted plaintext itself is
`{ version: 1, reference, secret }`, binding the entry to its reference. A `null` entry is a
tombstone. Unknown/future formats, malformed entries, and failed decryptions are refused before
replacement. Other ciphertext entries must also decrypt and validate before any write.

Electron `safeStorage` supplies encryption. An unavailable OS encryption service or Linux
`basic_text` backend fails closed. There is no plaintext, localStorage, or base64-only fallback
for persistent provider keys. The selected-backend API is queried only on Linux; macOS uses
Keychain. Errors distinguish unavailable encryption, locked/failed keychain operations, invalid
or unsupported vault files, and failed durable writes without exposing raw OS error details.

[`credential-files.ts`](../../electron/src/main/credential-files.ts) publishes a mutation as follows:

1. Read and validate the current document. File reads are bounded to 4 MiB; a failed read is not
   treated as an empty vault.
2. Encrypt and decrypt-check the new value in memory. Queue mutations on the vault instance so
   concurrent changes do not lose entries.
3. Create a uniquely named adjacent temporary file with exclusive creation and mode `0600`.
4. Write the complete encrypted document, fsync the file, and close it.
5. Rename it atomically over the destination, fsync the parent directory, and close the directory.
6. Read back and validate the published entry before resolving the mutation promise.

A failure before rename preserves the previous file. A failure after rename still rejects the
promise, even if the replacement is visible; the caller must not report durable success. Retry
reads the actual file rather than a decrypted cache. Temporary-file cleanup is best effort.
Orphan files from an interrupted process are not imported. Documents are limited to 4,096 entries;
capacity exhaustion fails the write rather than publishing an unreadable document.

Serialization is within the trusted vault instance in one process. There is no cross-process
file lock or support for independent writers sharing one vault file. Electron composes one
trusted singleton per file. Qualification is macOS-first; other OS keychain implementations and
directory-fsync behavior need their own native verification.

## Provider association and migration

[`ProviderCredentials`](../../src/modules/assistant/backend/providers/provider-credentials.ts)
owns resolution and migration. The
[`secret_ref` migration](../../src/modules/assistant/backend/migrations/0015_provider_secret_refs.sql)
adds a nullable opaque reference to provider configuration. For an existing plaintext `api_key`:

1. Create a fresh reference and write the key through the encrypted vault.
2. Read the reference back and verify the exact key.
3. In a SQLite transaction, verify the provider row still matches the original row, associate the
   new reference, and clear `api_key`.

If encryption, readback, or durable publication fails, the existing SQLite value is not cleared.
If the process stops after vault publication but before row association, an unassociated encrypted
entry can remain; migration can retry without destroying its original credential copy. A failed
association does not delete a valid encrypted copy.

Rotation creates a fresh immutable reference. Existing runs pin their provider snapshot and
reference, so later configuration changes cannot switch their credentials. Clear and provider
deletion remove the active association but retain historical encrypted references for those
pinned runs. Garbage collection and a historical-reference retention policy are not implemented.
Clearing a provider therefore does not promise immediate erasure of every historical key.

[`buildAiProviderClient`](../../src/modules/assistant/backend/providers/openpcb-provider-factory.ts)
resolves a reference only when building a client. Provider configuration and task snapshots carry
references, not saved API keys; public DTOs expose only credential-presence metadata and a generic
mask. A local provider with no configured secret does not consult the keychain and remains usable
when OS encryption is unavailable. A provider with a configured secret must resolve it successfully;
it cannot silently omit the key or switch to another provider. The managed OpenPCB Cloud bearer
continues through its separate transient cloud-session path.

The app-owned [AgentKit host](../../src/modules/assistant/backend/agentkit-host.ts) pins an
immutable provider generation containing the endpoint, selected model, effective tool capabilities
and opaque credential reference before queueing a turn. Its
[provider adapter](../../src/modules/assistant/backend/agentkit/providers.ts) resolves the app vault
inside the trusted process and refuses missing configured secrets. Generic framework provider CRUD
is not the public configuration path.

The [stream redactor](../../src/modules/assistant/backend/agentkit/redaction.ts) buffers only a
possible prefix of the raw or URI-encoded key before publishing text deltas, preventing adjacent
persisted events from reconstructing an echoed credential. Successful completion flushes an innocent
trailing prefix; failure or cancellation discards it, which can trim innocent text matching a key
prefix. Buffer size is bounded by the longest key representation minus one character. These checks
protect exercised provider response surfaces, not arbitrary secret exfiltration by trusted code.

Clearing `api_key` in SQLite is a logical migration, not forensic erasure. Old SQLite pages, WAL
files, snapshots, backups, prior task snapshots, and prior logs can contain credentials written
by older versions. These files are not automatically scrubbed. New secret-canary tests do not
prove that historical user data is clean. Database maintenance, backup handling, and key rotation
require a separate explicit policy.

## Isolated Supabase compatibility

The existing frontend cloud adapter still needs renderer-readable `get`, `set`, and `remove` for
Supabase sessions. Its caller is
[`cloud/supabase.ts`](../../src/core/frontend/src/cloud/supabase.ts), configured with storage key
`openpcb.auth`. The installed Supabase auth implementation also accesses its PKCE verifier and
optional user-storage suffix. The compatibility IPC accepts exactly:

- `openpcb.auth`
- `openpcb.auth-code-verifier`
- `openpcb.auth-user`

[`secure-storage.ts`](../../electron/src/main/secure-storage.ts) delegates only those keys to
[`CloudCredentialStorage`](../../electron/src/main/credential-cloud-storage.ts). They use a separate
`cloud-credential-vault.json`, with the same encryption and durable publication protocol. The bridge
cannot read, write, or clear provider references or the reserved session namespace. Cloud writes
are limited to 256 KiB in UTF-8 and use the same sender checks.

An existing `secure-store.json` is read only for one of these cloud keys. A legacy entry must decrypt
with the available OS encryption service before it can be copied and read back in the new cloud
vault. The legacy file is never modified. Uncertain plaintext/base64-only or invalid entries require
reconnection and remain untouched. A new explicitly submitted cloud session can be written to the
new vault without rewriting that legacy file. Durable tombstones prevent cleared sessions from
being resurrected from it after restart.

This is a constrained compatibility boundary, not a claim that cloud tokens are renderer-private.
Supabase still consumes its own session tokens in the trusted app renderer. The browser-only cloud
adapter also retains its existing localStorage behavior; it is not a provider-key vault. Historical
`secure-store.json` files and their backups can contain plaintext-equivalent legacy values and are
not automatically sanitized.

## Verification commands and evidence limits

Deterministic tests use an injected synthetic keychain and temporary/memory files; they do not read
real credentials or the user's vault:

```sh
bun test electron/tests/credential-*.test.ts
npx tsc --noEmit --target es2022 --module esnext --moduleResolution bundler \
  --strict --esModuleInterop --skipLibCheck --noUncheckedIndexedAccess --types node,bun \
  electron/src/main/credential-*.ts electron/src/main/secure-storage.ts \
  electron/src/preload/index.ts electron/tests/credential-*.test.ts
bun test src/core/backend/tests/assistant-provider-credentials.test.ts
```

Coverage includes encryption unavailable/denied/locked, corrupt and future formats, swapped refs,
failed publication at each file/directory step, interrupted migration, concurrent writes, rotation,
restart from persisted bytes, legacy reconnect behavior, namespace isolation, hostile IPC senders,
oversized payloads, and static error redaction. Provider integration tests verify association and
provider behavior; canary checks apply to the surfaces explicitly exercised by those tests.

The app-owned host and stream redactor have a separate real Node SQLite gate:

```sh
npm run test:agentkit-host
```

It uses temporary app and AgentKit databases, deterministic provider transports, and an injected
credential vault. It covers pinned configuration, manual crash recovery, cancel shutdown, cumulative
budgets, schema refusal, idempotency conflicts, and split-key durable event replay. This desktop
profile requires Node or Electron; Bun does not load the native AgentKit Node store. This gate does
not prove a packaged GUI, OS vault persistence, live provider support, or domain tool correctness.

Run the separate native test explicitly on a machine with a usable OS keychain:

```sh
node scripts/credential-native-smoke.mjs
```

The runner builds only the native smoke entry with the installed esbuild and launches the installed
Electron binary six times against a fresh temporary profile. It writes a synthetic random canary,
exits, verifies OS decryption in another process, rotates it, verifies another process read, clears
it, and verifies absence after another process restart. Only the expected digest and opaque reference
cross process boundaries outside the encrypted vault. It checks `0600` and rejects plaintext or
base64-only canary persistence, emits sanitized JSON evidence with runtime versions and bundle hash,
and removes the temporary profile. It creates no window and never reads the user's OpenPCB profile
or real provider credentials. The OS may need to authorize the smoke app's own encryption-key access.

Native testing with the installed unpackaged Electron binary proves that specific runtime/profile
path. It does not qualify packaged OpenPCB keychain identity, power-loss behavior, an authenticated
local API, a real account, provider inference, or the complete migration/credential acceptance matrix.
A new vault instance in the same process is not evidence of process restart; the staged runner makes
that distinction explicit. Record actual commands, versions, stage results, and artifact hashes in
qualification evidence rather than treating this document as a completion record.
